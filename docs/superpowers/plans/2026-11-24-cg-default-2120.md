# context-guru and metrics push on by default; tool-prune deprecated on the local install (#2120)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every local install, new or existing, runs context-guru and pushes metrics. On the local install, the tool-prune list moves into context-guru's `toolfilter.remove`.

**Architecture:** The built-in config (`cmd/cortex/local.go`) drops tool-prune and gives context-guru an empty `toolfilter.remove`. Two new agentop migrations, beside `migrateBobPricing`, bring an existing `~/.cortex/config.yaml` to the same state. Setup, `configMigrationPending` and `agentop service install` call them. `agentop tools scan --write` writes to the new list. cortex warns at boot and reload when tool-prune is still in the list.

**Tech Stack:** Go 1.26.10, `gopkg.in/yaml.v3` node positions for text edits, `log/slog`.

**Spec:** GitHub issue rossoctl/cortex#2120 (the issue body is the spec; read it with `gh issue view 2120 -R rossoctl/cortex`). Every "Part N" and "rule N" below is the issue's numbering.

## Decisions made in this plan (no human was asked)

1. **Order check in agentop.** agentop does not link plugins, so it cannot call `pipeline.New`. Add `config.BodyReaderPlugins() []string` to `core/config` (the `config.PraxisOffSafe()` pattern): the names whose normalized capabilities have `ReadsBody` and no body write. A drift test in `core/plugins/all` computes the same set from `plugins.Catalog()` and fails on a difference. The migration's order check is: no name from `BodyReaderPlugins()` comes after the context-guru entry in `pipeline.outbound.plugins`. This is the `validateCapabilities` reader-after-mutator rule for a request-only writer. tool-prune and context-guru have the same body capabilities (`WritesRequestBody`, request only), so a replace at tool-prune's position never changes the result.
2. **Names rule 3 must not move.** In addition to `mcp__<a>` with no second `__` (the issue), rule 3 also refuses a name that starts with `skill__` (toolfilter reads it as a skill, not a tool) and a name that toolfilter's `validDeclName` rejects (charset `[A-Za-z0-9._:/-]`, 1 to 128 characters). Reason: context-guru `Configure` rejects such a name, and the proxy would not boot. `config.Load` does not catch it.
3. **Existing context-guru entry, engine shape.** A user `components.toolfilter` block replaces the preset's whole `toolfilter` block (context-guru `config.applyPreset`). And an `engine:` with `components:` but no `preset:` runs no preset. So rule 3 edits an existing context-guru entry only when its `engine` is (a) absent or null, or (b) has `preset:` in {`house`, `housellm`, `conservative`, `medium`, `high`, `xhigh`} and no `pipeline:` key. These presets have `toolfilter` in their pipeline and no `toolfilter:` block of their own (context-guru v0.7.7 `config/config.go:697-726,808-1047`). For (a), the migration writes `engine:` with `preset: xhigh` and the components. Any other shape (for example `ultrahigh`, which sets `toolfilter.defer: auto`) is a refused condition: tool-prune stays, and the printed line names the preset.
4. **Pending is a bool.** `configMigrationPending` keeps its signature. A new `configRestartPending(path string) bool` tells `configStep.plan` whether to set `env.configPinsPending` for the two new migrations.
5. **Release-notes line.** `scripts/release_notes.sh` builds the notes from PR titles. The PR body gets a "Release note" section with the line in T9. This is in the repository workflow, so no human step.
6. **One PR.** The estimate is about 1,900 counted lines, under the 2,000 limit.

## Review Focus

1. A config with a two-space document indent (every top-level key at column 3). Both migrations must insert at the document's own indent. Pinned in T3 and T5 tests.
2. A context-guru entry with no `config:` key at all (the plugin defaults to xhigh). Rule 3 must create `config.engine.preset: xhigh` with the components, not `engine.components` alone, which would turn every compaction off. Pinned in T3.
3. A tool-prune `remove:` in block form (`- name` per line) or flow form (`[a, b]`). The migration reads the names from the parsed node, so both work. Pinned in T3.
4. A config where the outbound list has a body reader (for example `sparc`) after the parsers and no context operator. Rule 2 must refuse with the hand-fix error, not write a config that the proxy refuses at boot. Pinned in T3.
5. Setup on a config from before both changes: one run must give "update the cortex config", set the restart, and a second run must give "(kept)". Pinned in T6.
