# Chat agent side of the translation hub (#1966) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The router can send a Chat Completions agent (OpenCode, Pi, Bob IDE) to a server that serves only Anthropic Messages. The agent gets valid Chat replies, streamed or not. The Chat usage parser reads LiteLLM's cache counts.

**Architecture:** `chat.Protocol` gets `pivot.ReplyEncoding` (new file `chat/encode_reply.go`), then `pivot.RequestDecoder` and `pivot.SourceHeaderRemover` (new file `chat/decode.go`). `translate.Decodes("chat-completions")` becomes true when the decoder exists, and then `inferencerouter`'s `route.plan` translates a Chat request to a server with `anthropic-messages` and no `chat-completions`. No change to the registry, `convert.go` or the listener code. `core/parse/inference`'s Chat usage parser reads `cache_creation_input_tokens` and `cache_read_input_tokens`.

**Tech Stack:** Go 1.26.10, standard library only.

**Spec:** GitHub issue rossoctl/cortex#1966 (`gh issue view 1966 -R rossoctl/cortex`). The issue is the spec. Rule numbers K1-K11 are the issue's rule numbers. Parent rules H1-H6 and P1 are in #1963. #1911 rules are in `docs/superpowers/plans/2026-11-17-translation-hub-1911.md`. #1964 rules (R2, R2c) are in `docs/superpowers/plans/2026-11-18-responses-decode-1964.md`. #1965 rules (S1-S17) and its decisions are in `docs/superpowers/plans/2026-11-18-anthropic-server-1965.md`. **Every implementer reads the issue rules that their task names before they start.**

## Decisions made for this plan (with reasons)

1. **Two PRs, not one.** The issue asks for one PR under 2,000 counted lines. The estimate is about 2,170 counted lines. Calibration: the Responses decoder with its tests and fixtures was about 1,050 lines (#1968), the Responses reply encoder with tests about 800 (#1969), and the Anthropic encoder about 640 (#1972). Per task: T1 870, T2 610, T3 75, T4 160, T5 430, T6 25. P1 has T2, T3 and T4 (845) and no parent. P2 has T1, T5 and T6 (1,325), with parent P1. Reason for this order: `translate.Decodes` makes the router translate a Chat request as soon as `DecodeRequest` exists, and `core/listener/forwardproxy/translate.go` refuses a translation whose source has no reply encoder. So the reply encoder (P1) must merge first. The reply encoder alone changes no route.
2. **`created`** in a reply is `now().Unix()` at the start event. `now` is a package variable `var now = time.Now` in `chat/encode_reply.go`, so that the unit tests in package `chat` set a fixed time. The golden tests in package `translate` cannot set it: they replace each `"created":<digits>` with `"created":0` before they compare (regexp `"created":[0-9]+`). Reason: the spec asks for the real time, and goldens need fixed bytes.
3. **Reply goldens reuse the Anthropic reply inputs.** The Chat reply golden test reads the inputs in `core/translate/testdata/responses-anthropic/reply/` (they are Anthropic replies, the same for every agent) and writes its goldens to `core/translate/testdata/chat-anthropic/reply/<input base name>.to-sse.golden` or `.to-json.golden`. With `include_usage` the name is `<input base name>.include-usage.to-sse.golden`. Reason: no copy of the same inputs. Those inputs cover each case of the spec: `text`, `thinking_signature`, `redacted_thinking`, `two_tools`, `max_tokens`, `refusal`, `stream_error`, `server_tool`, `error_429_rate_limit`, `error_529_overloaded`.
4. **A redacted_thinking block** gives its `thinking_blocks` chunk at its `block_start`, because the start event carries the data (`Event.Data`).
5. **A tool call with no input pieces** gets the arguments `"{}"`: one extra `arguments` piece `{}` at its `block_stop` in a stream, and `"arguments":"{}"` when not streamed. Reason: Chat agents parse arguments as JSON (the Responses encoder does the same).
6. **Stop reasons outside K5's list** (`pause_turn` and any other) give `finish_reason` `stop`.
7. **The stream error chunk** (K7) is `data: ` + `chat.Protocol{}.EncodeError(ev.Status, ev.ErrorType, ev.Message)` + `\n\n`. So `code` is `null`, the same as the not-streamed error body.
8. **A reply with no stop event and no error event** fails at `End` with status 502, type `api_error` and the message `msgEndedEarly` (`chat/reply.go`): in a stream as the K7 error chunk with no `[DONE]`, not streamed as the `EncodeError` body. Reason: a broken stream must not look complete (#1911 decision 5).
9. **Not streamed:** `content` joins the text of all text blocks. `reasoning_content` joins the text of all thinking blocks (signed or not). `thinking_blocks` has the signed thinking blocks and the redacted blocks, in reply order. `finish_reason` and `usage` as K5 and K6.
10. **Usage before stop.** The pivot reply decoders emit `EventUsage` before `EventStop` (#1965 decision 5). The encoder keeps the usage and writes it at `EventStop`. A reply with no usage event gives zero counts.
11. **Chat decoder: message and part members.** The decoder reads only the members that K3 names. A message member or a part member that K3 does not name is ignored and not recorded. Reason: P1 (rule K11). Decoding each message into a struct, as the Responses decoder does with its items, is what makes one pass fast. The top-level fields are all recorded (K4).
12. **Where the K3 drops are recorded:** `name` → the message's `Extra["chat-completions.name"]`. `detail` → the image block's `Extra["chat-completions.detail"]`. A `refusal` part or an assistant `refusal` member → the message's `Extra["chat-completions.refusal"]`. `function.strict` → the tool's `Extra["chat-completions.strict"]`. A user or tool part of a type that K3 does not name → the message's `Extra["chat-completions.<type>"]`. A part's `filename` → the block's `Extra["chat-completions.filename"]`. The value is the raw member, or `true` when the decoder has no raw value.
13. **Accepted defaults are not recorded:** `n` of 1, `response_format` of `{"type":"text"}`, `parallel_tool_calls: true`, and `stream_options` with only `include_usage`. Other members of `stream_options` → `Extra["chat-completions.stream_options.<member>"]`.
14. **`stream_options.include_usage`** goes to `Extra["chat-completions.include_usage"]` with its raw value, as K4 says. So the Anthropic encoder names `include_usage` in `dropped` (#1965 decision 21). This is true: Anthropic does not get the field. The reply encoder (T2) reads it: the value `true` turns on the separate usage chunk.
15. **More refusals** (each a `*pivot.RequestError`, status 400, type `invalid_request_error`, exact text):
    - a body that is not a JSON object, or a member of the wrong type: `the request body is not a valid Chat Completions request: <detail>`;
    - a message role that is not `system`, `developer`, `user`, `assistant` or `tool`: `the request body is not a valid Chat Completions request: a message has the role "<role>"`;
    - the top-level `function_call` (the legacy request field) and `functions`: the K3 legacy text, `Cortex cannot translate legacy function_call messages. Use tool_calls.`;
    - a tool whose type is not `function`: `Cortex cannot translate a tool of type "<type>".`;
    - tool call arguments that are not valid JSON: `the arguments of a call to the tool "<name>" are not valid JSON` (the Responses decoder's text);
    - an `image_url` that is not a base64 `data:` URL and not an `http(s)` URL: `an image_url must have a base64 data URL or an http(s) URL`;
    - a `file` with `file_data` that is not a `data:application/pdf;base64,` URL: `Cortex can translate only PDF files (file_data as a data:application/pdf;base64 URL).`
16. **`image_url` as a string** (some clients send `"image_url":"https://…"`) is accepted as the URL.
17. **Empty tool call arguments** (`""` or only spaces) give a `tool_use` block with nil `Input`. The Anthropic encoder sends `{}` (#1965 decision 16).
18. **`cache_control` in a tool message.** The `cache_control` of the last part of a `tool` message goes to the `tool_result` block's `CacheControl`. Markers on other parts of a tool message are ignored. Reason: this is the inverse of the Chat encoder's rule 14 (`chat/request.go`, `user`), so the round trip keeps the marker.
19. **`cache_control` values** are kept as the decoded value, written again with `marshal` (sorted keys). `{"type":"ephemeral"}` and `{"type":"ephemeral","ttl":"1h"}` keep their bytes.
20. **A message with no blocks** after the drops (for example an assistant message with only a `refusal` part) is left out. A string content of `""` gives one text block with `""` (K3).
21. **Consecutive `user` messages** stay separate pivot messages. Only a `user` message directly after `tool` messages joins (K3). Reason: the spec joins only there, and Anthropic accepts two user messages in a row.
22. **`tool_choice` values that K4 does not name** (another string, or an object whose `type` is not `function`) → not set, and `Extra["chat-completions.tool_choice"]` with the raw value. `parallel_tool_calls: false` with no `tool_choice` gives `ToolChoice{Type: "auto", DisableParallel: true}` (the Responses decoder does the same).
23. **Source headers (K2):** `RemoveSourceHeaders` deletes `OpenAI-Beta`, `OpenAI-Organization` and `OpenAI-Project`, case-insensitive. Nothing else.
24. **K10 round trip and the Chat encoder.** The round trip runs `chat.Protocol{}`'s decoder and encoder. Two facts of the Chat encoder (`chat/request.go`) make more differences than K10 lists. The test allows them, with these reasons:
    - The Chat encoder neither sends nor names `Extra` keys of its own prefix, and it adds `stream_options.include_usage` to a stream. So the test removes every `chat-completions.` key from `Extra` on both sides.
    - The Chat encoder refuses document blocks (#1911 rule 14). So the test removes `BlockDocument` blocks from the first decode before it encodes.
    - The Chat encoder joins the assistant text into one string (#1911 rule 15). So assistant text blocks come back as one text block, with no `cache_control`.
    - The Chat encoder moves tool-result images to a user message after the tool messages (#1911 rule 14), and the decoder joins that message after the results (K3). So tool-result images come back after the last `tool_result` block of their message, before the other blocks. A `tool_result` with no text comes back with one `""` text block.
    - A nil tool-use `Input` comes back as `{}`.
25. **K11 budget** applies to `chat.Protocol{}.DecodeRequest`, measured by `BenchmarkDecodeRequest` in `core/translate/chat/decode_bench_test.go`. A benchmark, not a timed test: a timed test fails at random on a busy CI host. The P2 PR body gives the `ns/op` value.
26. **Docs** say what the code does after P2: four translated pairs, Chat agents can read their source. The docs go in P2, because P1 changes no route.

## Review Focus

1. A stream with `include_usage` true: the usage chunk comes after the `finish_reason` chunk and before `[DONE]`, and the `finish_reason` chunk has no `usage`. Without it: `usage` is on the `finish_reason` chunk, and no chunk has `"choices":[]`. Test: `TestReplyEncoder_IncludeUsage` in T2.
2. Two consecutive `tool` messages and a `user` message after them give one user message: `tool_result`, `tool_result`, then the user blocks. Test: `TestDecodeRequest_ToolResultsJoin` in T1.
3. A thinking block with a signature in a stream: `reasoning_content` deltas, then at `block_stop` one `thinking_blocks` chunk with the whole text and the signature. Test: `TestReplyEncoder_ThinkingSignature` in T2.
4. A Chat body with only `prompt_tokens_details.cached_tokens` parses as today. A body with `cache_creation_input_tokens` takes it out of the plain input. Test: `TestChatUsage_CacheWrite` in T3.
5. The router change: a Chat request to `{anthropic-messages, responses}` is translated to Anthropic, `/v1/completions` is not. Tests in T5.

The new comment says: OpenAI sends no cache-write field; LiteLLM's `cache_creation_input_tokens` and `cache_read_input_tokens` are read when they are present; `prompt_tokens` includes both cache counts.
