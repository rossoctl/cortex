# Central metrics stack (OpenShift)

Proxies push their metrics here, and a manager reads the totals of many machines in one Grafana.
It serves Cortex and context-guru proxies alike, and replaces the VM stack in
`rossoctl/context-guru` `deploy/central/` (issue #898).

```
proxy --OTLP over HTTPS--> OpenShift router --> Collector --OTLP--> Prometheus --> Grafana
         (token: context-guru only) (edge TLS)                                   |
                                                                         +--> Alertmanager
```

No machine opens a port: each proxy pushes out, and Prometheus scrapes no proxy.

Design: [`docs/superpowers/specs/2026-11-18-central-collector-openshift-design.md`](../../docs/superpowers/specs/2026-11-18-central-collector-openshift-design.md).

## What is here

| Path | What it does |
|---|---|
| `base/otel-collector/otel-collector.yml` | Two receivers (4318 Cortex, with no token; 4319 context-guru, with a bearer token). Sets `proxy` from the receiver, keeps four labels, sends OTLP to Prometheus. |
| `base/prometheus/` | `prometheus.yml` (OTLP receiver, which turns the four kept resource attributes into labels; scrapes the stack only), `rules/recording.yml` (11 rules), `rules/alerts.yml` (10 alerts), `tests/alerts_test.yml`. |
| `base/alertmanager/alertmanager.yml` | Routes alerts. Ships no delivery method. |
| `base/grafana/` | Data source and dashboard provisioning; six dashboards generated by `gen_dashboards.py`. |
| `base/*/deployment.yaml`, `service.yaml`, `pvc.yaml` | One Deployment each; PVCs for Prometheus (25Gi), Alertmanager (1Gi) and Grafana (1Gi). |
| `overlays/openshift/` | Namespace `cortex-central`, the Routes, NetworkPolicies. |
| `components/` | Optional parts. `events/` (ClickHouse, for the accountant's structural events) is next. |
| `check.sh` | Static checks (below). |
| `smoke.sh` | Live test of a deployed stack (below). |

The config files were copied from `rossoctl/context-guru` at commit
`cd90d55cae982e29fcf026a34a25834ef35a64b9`. Since then this directory is their source of truth; it
does not follow later changes there. One change was made on purpose: authentication is on.

## Deploy

You need `oc`, logged in with edit rights in the namespace `cortex-central` (it must exist).

1. Create the two Secrets. The Cortex path takes no token, so only context-guru has one. Keep the values in files, not on the command line:

   ```sh
   umask 077; mkdir -p ~/.config/cortex-central; cd ~/.config/cortex-central
   for f in context-guru.txt grafana-admin-password; do
     [ -s $f ] || openssl rand -hex 32 | tr -d '\n' > $f
   done
   oc -n cortex-central create secret generic collector-tokens \
     --from-file=context-guru.txt
   oc -n cortex-central create secret generic grafana-admin \
     --from-file=password=grafana-admin-password
   ```

2. Check, then apply:

   ```sh
   oc apply -k deploy/central/overlays/openshift --dry-run=server
   oc apply -k deploy/central/overlays/openshift
   ```

3. Wait until four pods are ready: `oc -n cortex-central get pods`.

4. Run the smoke test (below).

A change to a config file gives the ConfigMap a new name, so `oc apply -k` rolls the pods that use
it. A change to a Secret does not: run `oc -n cortex-central rollout restart deploy/otel-collector`
(tokens) after it.

## Point a proxy at it

| Proxy | URL | Token |
|---|---|---|
| Cortex | `metrics_push.url: https://cortex-central.apps.epoc001.ete14.res.ibm.com/cortex` | none. A `metrics_push.token` is sent but ignored. |
| context-guru | `--metrics-push-url https://cortex-central.apps.epoc001.ete14.res.ibm.com/context-guru` | `--metrics-push-token`: the `context-guru.txt` value |

See [`docs/laptop-service.md`](../../docs/laptop-service.md) for
Cortex's `metrics_push` block. The router strips `/cortex` or `/context-guru`, so the collector
receives `/v1/metrics`.

The Routes use the cluster's default certificate, a public wildcard for
`*.apps.epoc001.ete14.res.ibm.com`, so a proxy needs no extra CA. If a proxy's system trust store
rejects it, the fix is a Route with its own certificate; a proxy has no CA setting.

## Authentication

**The Cortex receiver takes a push with no token**, so a default Cortex install pushes with no
setup. The cost: anyone who can reach the Route can write Cortex series, under any `machine` name.
The collector still decides `proxy` and the label set, so such a push cannot add a label or claim
to be context-guru.

The context-guru receiver requires `Authorization: Bearer <token>`. A push with no token or a
wrong token gets 401 and stores nothing.

- The context-guru token is shared by every context-guru install. It proves "a context-guru
  install", not which one: `machine` is still the sender's claim.
- Rotate a token: write a new value, recreate the Secret (`oc create secret ... --dry-run=client -o
  yaml | oc apply -f -`), restart the collector, then hand the new value to the proxies. Pushes with
  the old token fail until a proxy has the new one; the counters are cumulative, so nothing is lost.
- Tokens for each install, binding a token to a machine, and mutual TLS are tracked in
  rossoctl/context-guru#1130.

## Access

- **Grafana:** `https://grafana-cortex-central.apps.epoc001.ete14.res.ibm.com`. Log in as `admin`
  with the `grafana-admin-password` value. The Secret sets the password only when Grafana's database
  is created; after that, change it in Grafana. Add a user for each manager (Administration,
  Users). There is no sign-up and no anonymous access.
- **Prometheus and Alertmanager** have no Route. Use
  `oc -n cortex-central port-forward svc/prometheus 9090` (or `svc/alertmanager 9093`).
- NetworkPolicies let the router reach only the collector's receivers and Grafana.

## What is stored

Prometheus keeps metadata only, for 30 days or 20GB, whichever comes first: counters and
histograms with the labels `proxy`, `machine`, `preset`, `service_version`, `model`, `provider`,
`tier`, `component` and a few reason codes. No prompt, response, session ID or host name. `machine`
is a random install ID. Anyone with Grafana access can read it.

To stop the storage, delete the stack (`oc delete -k deploy/central/overlays/openshift`); this
deletes the PVCs and the data with them. To stop one install from sending, turn its push off.

## What is lost when something fails

Nothing is queued anywhere. Proxies send running totals every 60 seconds.

| Event | Effect |
|---|---|
| Collector or Prometheus down for a while | The next push after it returns carries the totals. No count is lost. The graph shows one step at that time, not a slope. |
| A proxy stops without a clean exit | The counts since its last successful push are lost: at most about one push interval (60 seconds by default, longer if pushes were failing or the interval is configured higher). |
| A machine is off for a day | Its totals resume when it is back. The days between are not in the graph. |
| A pod restarts | Prometheus, Alertmanager and Grafana keep their data on their PVCs. |

## Alerts

`alerts.yml` holds the alerts of the metrics spec. The thresholds are proposals; change them after
you have seen real data. Alertmanager ships with no delivery method, so alerts stay in its own list
until you add a webhook, e-mail or Slack receiver to `base/alertmanager/alertmanager.yml` and apply.

## Why OTLP into Prometheus, not remote write

A counter series is first sent with the value of its first increment. Without a 0 before it,
`increase()` loses that first sample: for each new label set, and after each proxy restart.
Prometheus stores that 0 at the OTel start time (`--enable-feature=created-timestamp-zero-ingestion`),
but only for data that comes in on its OTLP receiver, and only from v3.7.0 (prometheus#16951).
Remote write v1, which the collector's `prometheusremotewrite` exporter sends, carries no start time.
Tested on Docker with Prometheus 3.2.1, 3.6.0, 3.7.0 and 3.16.0 and collector 0.165.0:

- The OTLP path stores the same series, with the same names and labels, as the remote-write path did.
  So the series stored before the change continue.
- An existing series gets its 0 at a time older than its last sample. Prometheus drops that 0 as out
  of order, with no error, and the push is accepted.
- Upgrading Prometheus from 3.2.1 to 3.16.0 on the same volume keeps every series and sample.
- All 75 dashboard queries run through Grafana 11.6.0 against 3.16.0 with no error, and give the
  same results as on 3.2.1.

**The limit.** Prometheus stores the 0 only when the start time is inside its appendable window,
about one hour before its newest sample. The start time is the proxy's process start. So the 0 is
stored for a series born within about an hour of a start (the series that come back after a
restart: on 2026-11-19 the only cache break came one minute after a restart). It is silently dropped
for a series first incremented later (measured: 10 and 50 minutes stored, 2 hours and 2 days not).
For those, `inc()` in `gen_dashboards.py` still falls back to `last_over_time()`.

**Rollback.** The remote-write receiver is still on. To roll back the collector alone, set its
exporter back to `prometheusremotewrite` (git history). Rolling back the Prometheus image to 3.2.1
is not tested: a TSDB written by 3.16.0 may not open in 3.2.1.
